# Results

Every number below comes from actually running the code in this repo.
Regenerate the discovery, lateral-movement, and process-manipulation
numbers with `make lab-up` followed by the matching `make demo-*` target;
the network-segmentation and CI/CD identity numbers are standalone (`make
demo-network-segmentation`, `make demo-cicd`, no live lab needed).
Regenerate the prioritizer examples with `python3 -c "..."` shown inline
below, or write your own scenario in `vuln/ot_prioritizer.py`'s test
file.

## Discovery scenario: detection before vs. after a policy fix

`scenarios/scenario_discovery.py` runs a real port scan (7 real TCP
connection attempts, from a simulated IT-zone host at `127.0.0.30`,
against the turbine PLC, HVAC controller, and five decoy OT service
ports) through the live network tap, then evaluates the same real
captured records against two zone policies:

| | Before hardening | After hardening |
|---|---|---|
| Zone policy | `it-enterprise` mistakenly allowed onto SCADA/auxiliary zones | `it-enterprise` removed from the allow-list |
| Alerts raised | 1 (generic discovery only) | 8 |
| Cross-zone violations caught | **0 / 7** | **7 / 7** |
| Detection latency (first violation) | N/A (never detected) | 0.85s (measured, see `scenarios/results/discovery.json`) |

The "before" configuration isn't a strawman -- it's a genuine, common
starting mistake (an IT/OT integration project leaves a broader access
rule in place than intended), and the fix is a one-line policy change, not
new code. That's the point of separating zone policy from detection logic:
the same three rules in `detection/rules.py` catch the same real scan
differently depending on what's actually configured as "allowed," which is
exactly the kind of configuration-driven improvement a real OT security
team would ship as a change, not a code release.

Full raw output: `scenarios/results/discovery.json` (regenerated by
rerunning the scenario, not hand-edited).

## OT-aware vulnerability prioritization: two real worked examples

Run against `vuln/ot_prioritizer.py` directly:

**Isolated, high CVSS** -- a CVE with CVSS 9.8, on an engineering
workstation inside the SCADA zone, not internet-exposed, not reachable via
vendor remote access, no known public exploit, but the patch requires an
outage and a compensating firewall rule is available:

```
operational_risk: MEDIUM (49.2/100)
immediate_action: No immediate containment action required
patch_timing: Next approved maintenance window
```

**Exposed, lower CVSS** -- a CVE with CVSS 6.1, on a DMZ jump host,
reachable via the vendor remote-access conduit, with a publicly known
exploit, high safety and availability impact if triggered:

```
operational_risk: HIGH (71.4/100)
immediate_action: Restrict or suspend the vendor-access conduit reaching this asset pending review
patch_timing: Can be patched without a scheduled outage
```

The CVSS-only ranking would put the first finding well above the second.
The operational ranking flips it -- which is the entire argument for this
module existing: patch priority driven by exposure and blast radius, not
by CVSS alone. See `tests/test_ot_prioritizer.py` for the automated
version of this same claim.

## Lateral-movement scenario: a pivot neither hop alone catches

`scenarios/scenario_lateral_movement.py` runs a real two-hop connection
sequence through the live network tap: an IT-zone host (`127.0.0.30`)
reaches the DMZ jump host's management port, then -- after a simulated
3-second attacker dwell time -- the jump host itself (`127.0.0.20`)
reaches the engineering workstation's management port. Both hops are
individually allowed under the current zone policy (`dmz: [it-enterprise,
vendor-remote]`, `ot-engineering: [dmz]`); that's what a jump host is for.

| | Result |
|---|---|
| Real connection records captured | 2 |
| `cross_zone_violation` alerts (either hop alone) | 0 |
| `lateral_movement_pivot` alerts | 1 |
| Pivot detected | **yes** |

Neither hop trips the zone-allow-list check on its own -- that's correct,
both hops are legitimately allowed. `rule_lateral_movement_pivot` is a
sequence rule, not a single-record rule: it tracks which hosts were
recently reached as a *destination*, then flags one of them becoming a
*source* into a new zone shortly after. That's the actual lateral-movement
signal a static allow-list can never catch by itself.

Full raw output: `scenarios/results/lateral_movement.json` (regenerated by
rerunning `make demo-lateral-movement`, not hand-edited).

## Process-manipulation scenario: telling an unsafe write from a safe one

`scenarios/scenario_process_manipulation.py` sends real Modbus Write
Single Register commands, through a real `pymodbus` client, to the
turbine simulator's writable curtailment-setpoint register (40007): a
five-step ramped sequence (0% -> 5% -> 10% -> 15% -> 20% -> 25%), then one
abrupt jump (25% -> 100%, a 75-point change in a single write).

| | Result |
|---|---|
| Real Modbus writes sent | 7 |
| `unexpected_modbus_write` alerts (any write to this asset) | 7 / 7 |
| `unsafe_setpoint_write` alerts (abrupt change only) | 1 / 7 |
| Abrupt write correctly flagged unsafe | **yes** (delta 75) |
| Ramped steps correctly *not* flagged unsafe | **yes** |

Every single write trips the broader read-only-asset rule -- correct,
since nothing in this lab is supposed to write to it at all. Only the
abrupt jump trips the narrower safety-impact rule, because real turbine
controllers ramp a setpoint change gradually; a 75-point jump in one
command risks the kind of sudden drivetrain/blade-pitch stress a gradual
ramp doesn't. Both rules firing on the same write is intentional
defense-in-depth, not redundancy -- see `rule_unsafe_setpoint_write`'s
docstring in `detection/rules.py`.

Full raw output: `scenarios/results/process_manipulation.json`
(regenerated by rerunning `make demo-process-manipulation`, not
hand-edited).

## Network-segmentation scenario: enforcement, not just detection

`scenarios/scenario_network_segmentation.py` is the one scenario in this
repo that isn't testing detection -- it tests whether the kernel actually
*prevents* a disallowed connection. It builds real Linux network
namespaces (one per zone) connected through a router namespace running a
real nftables forward chain, generated directly from
`network_zones.json`'s `allowed_cross_zone` policy, then attempts a real
TCP connection for every (src_zone, dst_zone) pair the policy has an
opinion on.

| | Result |
|---|---|
| (src_zone, dst_zone) pairs tested | 20 |
| Allowed pairs that actually connected | 6 / 6 |
| Disallowed pairs actually blocked by the kernel | 14 / 14 |
| Cases matching the declared policy | **20 / 20** |

No case here relies on anything being logged or flagged after the fact --
a disallowed pair's connection attempt is refused/dropped by nftables
before it reaches the destination's listener. See STATUS.md's "Deliberate
substitutions" section for why network namespaces are used here instead
of the originally-planned Docker bridge network.

Full raw output: `scenarios/results/network_segmentation.json`
(regenerated by rerunning `make demo-network-segmentation`, not
hand-edited; needs root/CAP_NET_ADMIN).

## CI/CD identity scenario: over-permissioned deploy pipeline, before vs. after

`scenarios/scenario_cicd_identity.py` scans a small fictional GitHub
Actions pipeline that publishes signed turbine controller firmware/config
bundles via an OIDC-assumed AWS role (`cicd/vulnerable-workflow/`,
`cicd/hardened-workflow/`) using TrustGraph's real parser, graph builder,
and detection engine as an actual dependency (github.com/karkiram05/trustgraph;
this scenario does not reimplement attack-path analysis).

| | Before hardening | After hardening |
|---|---|---|
| Findings | 5 | 0 |
| Critical | 4 (overpermissioned token, wildcard OIDC trust, 2x unpinned action) | 0 |
| Medium | 1 (missing OIDC audience restriction) | 0 |

The vulnerable version's trust policy trusts *any* branch or workflow in
the whole fictional `offshore-wind-ops` GitHub org (`sub:
"repo:offshore-wind-ops/*:*"`, no `aud` check) to assume the role that
publishes OTA firmware bundles -- and per `cicd/vulnerable-workflow/resources.json`,
that same role can also reach `wind-farm-fleet-management-api`, the API
that pushes accepted bundles out to individual turbine controllers. The
hardened version scopes the trust policy to one repo/branch with an
audience restriction, pins both third-party actions to a commit SHA, and
drops the role's reachable resources to just the OTA bucket it actually
needs.

Building this also surfaced a real bug in TrustGraph itself: a
`resources.json` entry naming a role that doesn't match any
`trust-policies/*.json` filename used to get silently absorbed into the
graph as a bare node with no type, which then crashed graph traversal with
an unrelated-looking `KeyError` instead of naming the actual mismatch.
Fixed in `trustgraph/graph/builder.py` (raises a clear `ValueError` naming
the unmatched role and the known roles) with a regression test in
trustgraph's own suite.

Full raw output: `scenarios/results/cicd_identity.json` (regenerated by
rerunning `make demo-cicd`, not hand-edited).
